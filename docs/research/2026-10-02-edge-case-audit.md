# 递归解压工具 —— 边界条件与风险登记册

日期：2026-10-02
状态：**调研笔记（非设计规格）**。设计规格需在方案获批后写入 `docs/superpowers/specs/`。

**证据等级约定**
- 【实测】= 本次会话在本机（Windows 11 IoT LTSC / 7-Zip 26.01 / .NET Framework 4.8.09032 / PowerShell 5.1）真实测量所得
- 【审计】= 由对抗式子代理提出，**尚未实测**，可能不成立于本机或本版本
- 【文档】= 来自官方许可/文档

## 一、已验证的关键事实（实测证据）

| # | 结论 | 证据 |
|---|---|---|
| V1 | 原脚本的致命缺陷已复现：**解压失败仍删除原包**，损坏包与加密包均被删除，文件从未解出 | 【实测】 |
| V2 | `7z x -y` **不能**抑制密码交互提示，脚本会永久挂起在 `Enter password` | 【实测】 |
| V3 | 7-Zip 退出码：正常=0，损坏=2，错密码=2，缺密码(未传 `-p`, stdin 为 EOF)=255 | 【实测】 |
| V4 | 必须**始终显式传 `-p<候选>`**，否则 7z 会索要密码 → 这正是 V2 挂起的根因 | 【实测】 |
| V5 | 回收站删除在 csc 编译的 .NET Framework exe 中可用：`Microsoft.VisualBasic.FileIO.FileSystem.DeleteFile(..., RecycleOption.SendToRecycleBin)`，文件移出原目录、回收站计数 310→311、**可按名检索到，可恢复** | 【实测】 |
| V6 | 回收站**不是保证**：配额按卷设置，实测本机存在 3245MB / 3276MB 的小配额卷；超过配额的文件会被绕过并**永久删除**。空光驱 H:\ 无 `$Recycle.Bin` | 【实测】 |
| V7 | `csc /resource:` 二进制嵌入与 `GetManifestResourceStream` 回读完全无损（4096 字节 payload，0 处不匹配） | 【实测】 |
| V8 | 嵌入 `7z.exe`(576,512B) + `7z.dll`(1,908,736B) 后 exe = **2,489,856 B (2.37 MB)** | 【实测】 |
| V9 | `System.IO.Compression` / `Microsoft.VisualBasic` 均可被 csc 引用并编译通过 | 【实测】 |
| V10 | **隔离目录 + PATH 清洗为 System32** 下，单文件 `7z.exe` 可独立完成 zip 与 **7z/LZMA** 的解压（exit 0，产物真实存在）；`7z i` 亦自报 **Rar / Rar5** 格式与 Rar1/2/3/5 解码器。**7-Zip 26.01 的 7z.exe 不需要 7z.dll** | 【实测】 |
| V11 | `7z l -slt` 为机器可读清单（逐条 `Path`/`Size`/`Packed Size`/`Attributes`），可做预检；`x` 的尾部汇总给出 `Folders/Files/Size/Compressed`，**可作为"解压完整性核对"依据** | 【实测】 |
| V12 | `-bsp1 -bb1` 进度可解析（形如 `58% 2 - sub\big2.bin`），且输出**含 CR(0x0D)** → 解析器必须同时按 `\r` 切分 | 【实测】 |
| V13 | 非法开关 `-bsp9` → exit 7，证明开关校验真实有效，故 `-bsp1/-bb1` 确被接受 | 【实测】 |
| V14 | .NET Framework `ZipFile` 能力边界：普通 zip ✅、ZipCrypto ✅、**AES 加密 zip ❌**（`InvalidDataException: 不受支持的压缩方法`） | 【实测】 |
| V15 | 7-Zip 许可为 LGPL-2.1（7z.dll 另含 BSD-3/BSD-2 代码）+ unRAR 限制；二进制再分发**必须附带许可信息**；unRAR 限制针对"再造 RAR 压缩器"，仅解压不受限但**必须声明** | 【文档】 |
| V16 | .bat 文件为 GBK 编码却执行 `chcp 65001` → 中文全部变 U+FFFD（实测日志含 311 处）；另测 GBK 文件在本机环境下**即使去掉 chcp 仍乱码**，而 UTF-8（带/不带 BOM）+`chcp 65001` 正常 | 【实测】 |
| V17 | **7-Zip 会按归档条目创建符号链接（reparse point）**：非提权、exit 0，产物 `link` 属性为 `Archive, ReparsePoint`。绝对 Unix 目标（`/tmp/...`）会被 7z 重挂到输出目录之下 | 【实测】 |
| V18 | **相对 `..` 穿越型软链目标在 26.01 上被遏制**：构造 `link -> ..\target` + 条目 `link\PWNED.txt`，7z `x` 返回 **exit 2**，目标目录零污染、既有文件未变。**但 7z 仍在输出目录内留下了那个 reparse point**。该遏制属**版本相关行为**，不可作为安全保证 | 【实测】 |
| V19 | 本机**无需管理员即可创建符号链接**（Developer Mode 已启用）→ 软链向量在本环境是"活"的，不是纯理论 | 【实测】 |
| V20 | 本机 `C:\Windows\System32\tar.exe` **不存在**（该 LTSC 版未含 bsdtar）；GNU tar 1.35 位于 `C:\Program Files\Git\usr\bin\tar.exe`，且 **MSYS tar 不接受 `C:\` 形式的绝对路径**（会被当作远端主机），必须用相对路径或 MSYS 路径 | 【实测】 |

**推翻的审计结论（重要）**：打包审计断言"7z.exe 无 7z.dll 必然报 Can't load 7z.dll，故必须改用 7za.exe"。该结论对**旧版本**成立，对 7-Zip 26.01 **经实测不成立**（见 V10）。同时，另一审计称 `7za.exe` 不含 RAR —— 我们**不使用 7za.exe**，故该争议对本案无影响。仍建议同时嵌入 `7z.exe`+`7z.dll` 以消除版本差异风险。

## 二、风险登记册

### A. 删除与原包安全（最高危）

| # | 场景 | 后果 | 对策 | 等级 |
|---|---|---|---|---|
| A1 | 解压失败/部分失败仍删除原包 | 不可逆数据丢失 | 仅在**该包**校验通过后删除；致命错误绝不删 | 【实测】已复现 |
| A2 | 加密包：密码失败后仍删包 | 原包消失且内容从未解出 | 密码失败一律不删；失败必须有显著提示 | 【实测】已复现 |
| A3 | 大文件超过卷回收站配额 | UI 说"已移入回收站"，实际**永久删除** | 删前比对该卷配额与文件体积；不可保证时明确告知并提供"隔离文件夹"替代；删后**枚举回收站核实**，否则如实报"已永久删除" | 【实测】V6 |
| A4 | 目标是 UNC / 可移动介质 / exFAT | 无回收站，直接永久删除 | 先判 `GetDriveType`；`DRIVE_REMOTE`/`DRIVE_REMOVABLE` 默认禁止删除并要求二次确认 | 【审计】 |
| A5 | 删除默认开启或被误勾 | 100GB 级误删 | 默认**关闭**；独立"危险操作"区、红色、措辞写明后果；启动前二次确认且不默认聚焦 OK | 【审计】 |
| A6 | 以"删除成功"判断依据是 API 未抛异常 | 谎报可恢复 | 回收站能力视为**尽力而为、不可作为安全承诺** | 【审计】 |
| A7 | 清空/回滚"失败产物"时递归删目录 | 删掉非本次产生的用户数据 | 只删本次创建且记账过的路径，自底向上，删前复查 reparse point；优先改名 `(未完成)` 而非删除 | 【审计】 |

### B. 解压目标、覆盖与提交原子性

| # | 场景 | 后果 | 对策 | 等级 |
|---|---|---|---|---|
| B1 | `x` + `-y` 默认覆盖已存在文件 | 重跑用坏结果覆盖好文件，且**不在回收站**，无撤销 | 绝不向非空目录解压；已存在则改 `name (2)` 或中止；默认策略为**跳过**而非覆盖 | 【审计】 |
| B2 | 目标文件夹名与已存在的**文件**同名 | `CreateDirectory` 失败后回落到父目录 → 内容洒进父目录并被当作成功删除原包 | 建目录后立即复核"存在且为空"；失败即中止该包，**绝不回落父目录** | 【审计】 |
| B3 | 解压中途崩溃/断电 | 半成品与完整产物**外观无差别**，用户手删原包 | 解压前落哨兵文件，校验通过后才移除；产物目录名或哨兵明示"未完成" | 【审计】 |
| B4 | 提交（改名/移动）阶段失败 | 输出滞留暂存区，但日志已记为完成 | 固定顺序并记账：解压到暂存 → 校验 → **同卷改名**提交 → 复核 → 才考虑删原包 | 【审计】 |
| B5 | 暂存放 `%TEMP%`（可能跨卷） | 跨卷移动非原子，半移动状态 | 暂存必须放在**目标同卷**，保证改名原子性 | 【审计】 |
| B6 | 归档内两条目映射到同一输出文件（大小写、`a/./b` vs `a/b`、NFC/NFD、非法字符被改写、保留设备名） | 静默后者覆盖前者，退出码 0，用户少文件而不自知 | 解压前用 `l -slt` 构建条目→路径映射，按序数忽略大小写 + NFC 归一；冲突则拒绝或改名；解压后核对条目数 | 【审计】 |
| B7 | 归档条目名与 Windows 非法名/保留名（`CON`、`NUL`、`COM1`、尾点尾空格、`: ? * < > \| "`） | 静默改名、无法打开、或生成 ADS | 预扫描建改名映射；明确且固定 `-snt`/`-snc` 组合；将"磁盘名 ≠ 条目名"清单化告警且**不删原包** | 【审计】 |

### C. 递归与格式识别（第二大坑）

| # | 场景 | 后果 | 对策 | 等级 |
|---|---|---|---|---|
| C1 | 把 OOXML/APK/JAR/EPUB/ODF（本质是 zip）当压缩包递归解开 | Office 文档被拆成上千散文件；若开启删除 → **用户文档被销毁**，且全程 exit 0 | 递归必须**按内容身份**而非魔数放行：读前几个条目判定（`[Content_Types].xml`/`_rels/`→OOXML；`mimetype`=epub；`AndroidManifest.xml`+`classes.dex`→APK；`META-INF/MANIFEST.MF`+`.class`→JAR 等）；这些扩展名默认 deny，永不删除其原文件 | 【审计】高风险 |
| C2 | 默认不删原包 + "反复重扫直到没有" | 父压缩包始终在扫描树里 → **无限循环**重复解压 | 必须有持久化 processed-set（规范化全路径+大小+mtime）；每轮只扫描**上一轮新建**的路径，而非重扫全树 | 【审计】 |
| C3 | 图种/多态文件：`.jpg` 尾部附加 RAR/ZIP、`.exe` SFX、头部有前置垃圾的 ZIP | 只看偏移 0 → 误判"不是压缩包"而跳过，用户找不到内容 | 两段式检测：偏移 0 签名；失败则在前 ~2MB 内搜 `PK\x03\x04`/`Rar!`/`7z\xBC\xAF\x27\x1C`，并在尾部找 EOCD；作为"内嵌压缩包"提示，保留宿主文件 | 【审计】 |
| C4 | "防和谐"包：文件头被清零/改写 | 判为非压缩包而跳过，用户以为工具坏了 | 第三档判定：尾部 64KB 内找到 `PK\x05\x06`/`PK\x01\x02` → 报"头部损坏，可能可修复"，区别于"损坏" | 【审计】 |
| C5 | 静态链接库/设备节点/fifo 条目 7z 无法如实落盘 | exit 0 但**并非每条都写出** | 成功判定必须基于**索引比对**（条目数+总字节）而非退出码 | 【审计】 |
| C6 | 归档内 symlink/junction/hardlink 条目 + 通过该链接写入的后续条目 | 7-Zip **确实会创建 reparse point**（V17 已实测），输出树里会留下一个指向外部的链接；本版 26.01 拒绝了穿越写入（V18），但该遏制属**版本相关行为**——安全属性不能依赖解压器的"好脾气"，且历史上此处有在野利用漏洞（符号链接目录穿越，25.00 前） | 索引先行，拒绝/展平 reparse point 条目；解压后遍历暂存树断言**零 reparse point** 再提交；**版本下限 25.00** | 【实测】V17/V18 |
| C7 | 条目名含 `..`、前导 `/`、盘符、UNC | 写到目标之外，或触发 SMB 外联泄露凭据 | 自行校验（不依赖 7z 的好脾气）：`Path.GetFullPath` 归一后必须是暂存根的严格子路径；**每一层嵌套都要校验** | 【审计】 |
| C8 | `desktop.ini` 的 `IconResource` 指向远端 | Windows 自动拉取 → NTLM 凭据泄露 | 视作告警项 | 【审计】 |

### D. 分卷

| # | 场景 | 后果 | 对策 | 等级 |
|---|---|---|---|---|
| D1 | 各分卷族**权威成员不同**：`.zip`+`.z01` 中 `.zip` 是**最后一个**卷；`.rar`/`.r00` 中 `.rar` 是**第一个**；`.part1.rar`、`.7z.001` 是第一个 | 指错成员 → "无法作为压缩包打开"，被误读为下载损坏 | 硬编码分卷族表（权威成员 + 连续性规则）；缺卷报**具体缺哪一个** | 【审计】 |
| D2 | 把 RAR 分卷当字节切分去**拼接** | RAR 每卷有独立头，拼接即损坏；200GB 还要再占一份空间 | 默认**不拼接**，把权威成员交给 7z 自行按名寻卷；仅当各分片**确不以归档签名开头**（真字节切分）才流式拼接并预检空间 | 【审计】 |
| D3 | 伪装卷名：`movie.7z.001` → `movie.7z.00删1`（**数字中间插垃圾**）、随机化基名、后缀整体剥离 | 仅剥尾部后缀**无法**重组，7z 按传入名推算后续卷名 → 找不到第 2 卷 | 规则去伪装 + **暂存区规范名验证**（同卷硬链接优先，避免 200GB 复制）；验证失败则回滚改名 | 【审计】 |
| D4 | 分组误判：`CD1.rar`/`CD2.rar`、每个 `.001` 其实是独立完整压缩包 | 拼错或按分卷解析 → 损坏或貌似完整的不完整产物 | 卷语法须为**终止式 token** 且基名一致、位宽一致、无空洞；若每片都带完整归档签名则判为独立；**先出分组预览表**供用户纠正 | 【审计】 |

### E. 密码

| # | 场景 | 后果 | 对策 | 等级 |
|---|---|---|---|---|
| E1 | 密码线索在文件名/文件夹名/`解压密码.txt`/`必看.txt`/readme/url 域名/归档注释里，或只在网盘分享页 | 完全错过"近在眼前"的密码，报"需要密码" | **任何改名/移动/删除之前**先采集候选：文件名、目录名、同目录小文本文件（≤256KB 的 txt/nfo/md/url/html/ini）、`l -slt` 的归档注释、URL 域名；生成变体（去括号、裁空白、全角转半角、去零宽/NBSP、前缀剥离、纯域名）；区分"提取码"与"解压密码" | 【审计】 |
| E2 | RAR 头加密（`-hp`） | `7z l` 对"错密码/损坏/非归档"**表现相同** → 误报损坏 | 用候选密码走 `l`/`t` 探测（**不要用 `x`**，否则每次错误猜测都写大量垃圾），区分"已加密未知密码"与"不可读/损坏" | 【审计】 |
| E3 | 错误密码在 ZipCrypto 上有 1/256 头校验通过，写出垃圾后 CRC 报错 | 静默写入**字节错误但文件名正确**的文件；且"复用上次成功密码"会把假阳性扩散到全批次 | 只有 exit 0 才算完全成功；缓存密码前必须用 `t` 验证；非 0 退出的产物标记为不可信 | 【审计】 |
| E4 | 密码经 argv 传递 | 同机他进程可读（任务管理器/WMI），且易进日志 | 不记录密码；若 7z 版本不支持非 argv 通道，**在 UI 中如实说明**该暴露面 | 【审计】 |
| E5 | 密码含尾空格/中文/全角数字/零宽字符；密码文件为 UTF-16LE 或 GBK+BOM | 用户看着屏幕上的密码却被告知错误 —— 最伤信任的一类提示 | 候选阶梯显式化并展示；密码文件按 BOM/可解码性探测（UTF-8 → GBK → UTF-16）；**记录命中的是哪一个候选** | 【审计】 |
| E6 | 每层密码不同 | 全局缓存导致后续层静默失败 | 密码成功必须**按归档**记录，全局仅作"下一个首选候选" | 【审计】 |

### F. 资源、炸弹与路径长度

| # | 场景 | 后果 | 对策 | 等级 |
|---|---|---|---|---|
| F1 | 磁盘写满（默认保留原包 ⇒ 峰值 ≈ 2× 源体积；递归每轮再加一份） | 中途 I/O 失败，产物貌似完整，用户手删原包 | 用 `l -slt` 预算总解压体积 vs `GetDiskFreeSpaceEx`，要求 ×1.1 + 回收站预留；运行中轮询剩余空间并在低水位**干净中止**而非级联报错 | 【审计】 |
| F2 | 解压比炸弹（50KB→40GB）、海量条目（2MB→300 万条目） | 磁盘打满 / MFT 与配额耗尽 / AV 逐文件扫描导致事实性卡死 | 解压前按索引执行上限：最大压缩比、单包最大解压体积、最大条目数、单文件上限；**跨整个运行**累计预算 | 【审计】 |
| F3 | Quine 自包含归档 / A 含 B、B 含 A | 每轮翻倍直至上限；开启删除时还会毁掉正在复制的东西 | 按**内容哈希**（非文件名）维护全局 visited 集；配合深度上限与累计预算；深度触顶要**显式列出未处理项** | 【审计】 |
| F4 | 深层嵌套 + 中文名超 MAX_PATH(260) | 7z 内部可能用 `\\?\` 写成功，而**我方**的 .NET 枚举/校验/删除调用失败 → 递归"找不到东西了"却报成功；回收站（shell API）同样受限 | 预计算最长输出路径，超阈值拒绝；manifest 声明 `longPathAware` + AppContext 开关；枚举用 `\\?\` 前缀；**路径超限的包永不删除原包** | 【审计】 |

## 四、对架构的三个结论性影响

1. **成功判定必须基于"归档索引比对"（条目数 + 总字节，必要时逐文件哈希），而不是 7-Zip 的退出码。** 只看退出码是与原脚本"从不检查错误码"**同一类**的 bug，只是更隐蔽。→ 直接对应 V11（`l -slt` + `x` 尾部汇总）。
2. **"解压到目标同卷的空暂存目录 → 校验 → 改名提交"是单点最高杠杆的改动**，一次性覆盖 B1/B2/B3/B4/B5、C6、C7、F1 与 A7。
3. **"删除走回收站"必须加一层"诚实性"处理**（卷类型 + 配额 + 删后核实），**不可在 UI 上承诺为可靠撤销**；不满足条件时必须如实告知，并提供"隔离文件夹"替代。→ 直接对应 V6。
